# Magnific 高清放大与 Agent 本机验收

日期：2026-10-05。覆盖独立原生接口、正式增强面板、Agent 审批与持久保存；本批未使用真实 Key、未调用收费模型。页面截图中的陶瓶图片与供应商响应均为本机合成素材，不证明真实放大效果或倍率质量。

## 参考与实现

- 安装包的 `Sge` 包装器与 `DB` 面板确认 Magnific 四项设置，公开文档确认现行 `api.magnific.com` 的 Precision V2 POST/GET 与 `x-magnific-api-key`。没有使用 TapNow 私有接口。[精确合同及最小来源证据](MAGNIFIC-PRECISION-NATIVE-CONTRACT-20261005.md)。
- Computer Use 在官方网页实际打开“增强 → 高清放大 → Magnific”，读到锐化7、颗粒7、细节30、倍率2；三个强度滑杆0–100、倍率2–8。没有点击官方 Generate。此次创建的唯一空测试节点已删除，重新加载后 DOM 确认不存在，原来源节点仍在；账号画布截图没有发布。
- `server/generation-magnific*.cjs` 实现四参严格映射、完整原尺寸 PNG 输入、原 UUID checkpoint、GET 恢复、安全结果下载与 PNG/JPEG/WebP 完整解码。原生协议由网关和多供应商路由共同支持，元数据保留精确公开型号。
- `src/features/image-upscale/` 实现前端合同及原尺寸媒体准备。`generation-ui.js` 只为明确选中的 `magnific-native` 使用该路径；旧 `tasks-v1` 网关仍须自行实现四参，fal 不被冒充为 Magnific。
- Agent 的 `generation_submit` 支持明确 `upscale` 四参、新建相连增强节点和 `targetNodeId` 指定目标；来源、项目、选区、参数和配置变化会阻断过期请求。`sourceClip` 纳入完整来源守卫。

## 正式页面实操

隔离入口由 [QA宿主](../src/features/image-upscale/qa/README.md) 创建，独立 IndexedDB 与临时服务端归档，不读取日常画布或真实环境配置。供应商边界使用固定合成响应，正式面板、TaskService、网关、原生适配、PNG完整验证、结果归档与画布保存未替换。

| 操作 | 实际观察 |
| --- | --- |
| 缺配置 → 配置恢复 | 正式“开始增强”先禁用，再恢复；没有供应商 POST |
| 四滑杆键盘调整 | 倍率3、锐化8、颗粒8、细节31原样到达后端；来源512×320、3029字节，无缩图 |
| 首次结果保存失败 | 生成成功但显示“结果待保存”；第一次保存失败，正式重试后保存次数1→2，POST仍1、节点版本仍1 |
| 未知状态 → 查询原任务 | 面板显示“查询原增强任务”；三次GET使用同一原UUID，释放结果后成功，POST仍2、版本增为2 |
| 两级 Escape | 模型菜单打开时第一次Escape只关菜单；第二次关闭参数面板 |
| 配置返回前关闭 | 开始增强后延迟配置，Escape关闭再释放响应，POST保持2，没有迟到派发 |
| Agent 新建增强节点 | 正式审批显示倍率3、锐化14、颗粒29、细节41及新建目标；批准后先持久任务ID，再读取原尺寸PNG并POST；新增一个带来源连线的增强节点，版本1 |
| Agent 写回已有增强节点 | 审批显示明确目标ID；批准后保持同一节点与连线，版本1→2；总生成POST为4 |
| 刷新恢复 | 原源图和两张结果均complete；实际尺寸512×320、768×512、768×512；两个增强节点各2版本，客户端POST为0、供应商累计POST仍4 |
| 日志与隔离 | 最终浏览器warn/error为空；夹具审计的外部请求阻断计数和其他生产API计数均为0 |

固定合成输出是768×512，与选择倍率无关。验证的是参数、状态、媒体和保存链路；没有使用该图片验证供应商的实际3倍放大能力。

## 专项检查与交审

- 原生供应商14项：精确POST字段、四参范围、输入完整解码、UUID保存顺序、原任务查询、真实FFmpeg JPEG/WebP解码、原始字节归档与不重POST。
- direct/routed 网关集成4项：真实媒体HTTP读取、服务重启、坏首PNG保留原身份后恢复，以及下载构造钩子不得进入浏览器/JSON配置。
- Agent Magnific12项；同时检查相邻皮肤、图片处理和执行模块，共37项通过。
- 前端Magnific7项、增强6项、皮肤6项；QA宿主HTTP2项。完整请求也在旧网关配置判断前校验。
- 相邻路由34项首次31项通过；3项失败来自旧夹具。API配置VM缺少`structuredClone`，媒体路由仅模拟供应商API、未提供实际下载媒体。补齐真实环境及合成PNG/MP4后，相关文件分别15/15、5/5通过，其余路由14项此前通过。后者在独立抽取的`d419371`基线也复现两项失败，修正夹具后基线同样5/5通过；没有放宽生产验证。
- 合同负责人只读复核原生适配；Agent负责人交审前端守卫；供应商负责人交审共享路由及媒体接线，未发现剩余阻断。未运行全库测试。

## 配置与开放项

按[原生配置](MAGNIFIC-NATIVE-20261005.md)合并供应商、精确模型映射和路由，再填写自己的 Magnific Key。此协议不需要公网源图托管；结果为JPEG/WebP或其他支持的PNG编码时需要已安装的FFmpeg/FFprobe。下载钩子仅为可信Node构造器的测试注入，不能经HTTP请求、供应商JSON或配置API传入。

真实Key、账号资格、配额、费用和生成质量仍需验收；没有远端取消接口，不把本机取消解释为供应商已停止计费。皮肤原生、视频首次识别、Ark本地视频公网发布、SPZ以及全站逐态/品牌清点仍在[全局进度](STATUS.md)的开放范围，本批不是全站完成声明。
