本轮将预算内本地 SPZ 从全量绘制改为官方 Gaussian 层级选择。原 SPZ、全量 packed/SH 数据和权威 Group 文档保留；派生 LOD 树及当前选择只属于单个渲染上下文。近远移动按摄影机与真实像素尺寸改变合并层级，未用随机/固定间隔抽点伪装 LOD。新定向9/9及单项混合拾取1/1通过；主任务已确认真实GPU近远切换、预算、鼠标拾取、删末源释放/撤销及刷新恢复、PNG解码与视频播放。跨视图mesh.context覆盖已补修，追加回归2/2、独立只读交审及root2有镜头实机复验均通过。未把文件级视频检查计入完成。

## 路径与官方证据

- [官方 LOD 入门](https://sparkjs.dev/docs/lod-getting-started/)支持在后台 Worker 对 SPZ 构建真实树；默认实时 `tiny-lod`，更慢的 `bhatt-lod`/quality 推荐离线预构建 RAD。该文档给出的约 1–3 秒/百万源点是官方说明，不是本项目跨设备性能承诺。
- [官方按需渲染](https://sparkjs.dev/docs/on-demand-rendering/)要求异步排序/LOD 完成后继续处理 dirty 请求；[性能说明](https://sparkjs.dev/docs/performance/)区分 Gaussian 数量、投影覆盖和 GPU 混合负载，低数量本身不证明帧率。
- 已安装 Spark **2.3.1**：`dist/spark.module.js:8310` 的 `PackedSplats.createLodSplats`复制原 packed/SH 输入，调用官方 `tinyLodPackedSplats` Worker/WASM，派生结果保存到 `lodSplats`，原数据保留。`SplatMesh.createLodSplats`在10924行委托该实现。
- 2.3.1 `SparkRenderer.driveLod`（12604附近）计算像素尺度/总预算；`driveLodExclusive`（12673）初始化原生树、调用 `traverseLodTrees`、生成官方 indices。不是项目自行实现 Gaussian 聚类或粗略射线体。
- 本机原安装包 `/Applications/TapNow.app/Contents/Resources/web/assets/spark.module-LMeSeoEa.js`也包含同类 `tinyLodPackedSplats`/`qualityLodPackedSplats`、`lodSplatCount`、`lodRenderScale`和原生 Worker 路径；只作接口对照，未复制其业务模块或调用原站 API。

采用已批准且已安装的 SDK 实时 tiny-lod，适合当前只接受本地 SPZ 的结构，不增加 RAD 资源格式、编译器、依赖或外部转换服务。本轮不声明实现 RAD 按页流式加载。

250,000是每个view的绘制/排序预算，**不限制全量解码、派生树或源GPU纹理的驻留内存**。原压缩/展开/源数量限制继续生效；未声称可在固定内存内导入任意大SPZ，也未提供FPS/零掉帧承诺。

## 必要的 2.3.1 适配

1. SDK `update()`内部启动`driveLod()`但不await。项目关闭自动drive，仅在独立 `splat-lod.mjs`中同步发起原生drive，并捕获/等待其官方worker exclusive任务，再执行唯一GPU累积/排序。首次累积不会先走全量；完成后才写入视角缓存，idle帧不反复排序。
2. SDK复用index纹理时仅上传GPU，不同步`instance.indices/texture.image.data`；而native raycast读取该CPU数组。适配器将**同一官方选择结果**同步回CPU数据，未另取采样；尚未注册GPU的纹理标记needsUpdate。
3. SDK `dispose()`先获取Map live iterator再clear，导致旧indices texture迭代为空。上下文在clear前显式dispose所有索引纹理。删除对象亦释放对应worker tree，不等待隐藏超时。

上述桥接依据精确安装版本，SDK升级需复核接口及回归。本轮只临时修改自己renderer实例的原生分发方法，不修改SDK原文件、全局prototype或共享worker。

## 终验发现并补修的跨视图状态覆盖

最后诊断`current.sources[0].renderedCount=786,233`，但主`drawCount/activeCount=249,999`。这未说明GPU预算失效：Spark 2.3.1 `onBeforeRender`（12432行）实际`geometry.instanceCount`来自本renderer的`activeSplats`，绘制数据来自其`display`累积结果。专项诊断的`renderedCount`却读取`SplatMesh.context.numSplats`，不是绘制统计。

只读源码确认了覆盖路径：主片场与shot的两个SplatContext具有不同GPU mesh，但使用同一`rt.scene`。SDK `prepareGenerate`（11956/11976附近）通过`scene.traverse`收集并frameUpdate**包括隐藏layer在内**的所有SplatGenerator；另一个renderer的LOD map不含当前mesh，传入undefined indices。`SplatMesh.update`（10763–10770）因此关闭其context LOD并写回全源count。

该现象不能只归类为诊断字段误报：官方raycast（10852–10855）同样读取该mesh.context；如果相机key未变，项目settle会复用已完成累积，而不会重新绑定被覆盖的context，可能对全源数据射线测试。GPU预算、上述浏览器图像/播放证据仍成立。

root授权后，最小补修仅将`SplatContext.enqueue`内的原生`SparkRenderer.update`遍历根从共享`this.scene`改为本context的`this.layer`。已安装SDK的`updateInternal → prepareGenerate`只要求root提供`traverse/traverseVisible`，实际`THREE.Group`具备该合同；渲染仍使用原正式scene，不修改任何父子归属、全局prototype或SDK源文件。当前产品未使用全局SplatEdit，proxy变换/可见性与对象世界矩阵继续沿原父链生效。
